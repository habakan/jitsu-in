# なぜこの形なのか

README では概要と使い方を説明します。この文書では**設計理由**を説明します。
構成は [../ARCHITECTURE.md](ARCHITECTURE.md)、実行環境は [everywhere.md](../everywhere.md) をご覧ください。

## なぜ2つに分けるのか

署名器の中で、攻撃者が選んだバイト列を読む最も複雑なコードは解析器です。解析器を隔離すると、
乗っ取られても鍵には届きません。鍵を持つモジュールとは別で、そのモジュールからホスト関数を呼べないためです。

**乗っ取られた解析器が取引について嘘をつくのを防ぐのは、サンドボックスではなく plan です。**
署名側は鍵をすべて再導出し、お釣りかどうかを判定し、手数料を計算します。表示する文字列も plan の
バイト列から組み立てます。さらに SHA-256 が一致する plan にだけ署名します。そのため、悪意ある解析器は
表示した取引への署名を求めることはできますが、表示した取引とは別の取引に署名させることはできません。

## 何のためにあるのか

Bitcoin では、ルールや取引を利用者自身が検証できます。署名ソフトは鍵を扱い、何に署名するかを決めるため、
コード全体を確認するのが難しいです。

**jitsu-in は署名ソフトを検証しやすくすることを目指しています。** 手段は2つあります。

**ホスト関数を使わず、ビルドツールを固定します。** どちらのモジュールも import は 0 個です。ビルドに
パッケージマネージャは使わず、ツールチェーンのバージョンとハッシュを固定しています。`parser.wasm` は C の4ファイルから
ビルドされ、15,632 byte です。

> バージョンとハッシュを固定すると、同じビルドを再現し、使っている依存を特定しやすくなります。監査していない依存が
> 安全になるわけではありません。依存の確認は別途必要です。

**同じモジュールを複数のプラットフォームで動かします。** 同じ wasm ファイルが、OS のないマイコン、
ブラウザ、Android、iOS で動きます。複数のランタイムで出力を比べると、実行結果の違いを確認できます。
共有モジュールの修正は、そのバージョンを使う環境すべてに反映されます。ランタイムやホストの不具合は別に修正する必要があります。

実行した環境と確認した内容は[プラットフォーム図](../everywhere.md)にまとめています。

## 何を確かめられるのか

| | |
|---|---|
| **import が無い** | どちらのモジュールもホスト関数を呼べません。時計、ネットワーク、システムコールもありません。CI で検証しています |
| **メモリが伸びない** | `--no-growable-memory` でビルドしているため、宣言した以上のホストメモリを使いません |
| **要求する機能を固定** | [Lime1](https://github.com/WebAssembly/tool-conventions/blob/main/Lime.md) に固定しています。リンク時に検査するため、依存が要求ランタイムを広げるとビルドに失敗します |
| **再現可能** | バージョンとハッシュを固定したツールチェーンを使うと、macOS arm64 と Linux x86_64 で同じバイト列を生成します |
| **Bitcoin Core と同じ答え** | 解析結果は37件で一致し、署名8本も ECDSA、Schnorr ともにバイト単位で一致します |
| **ホストが一致** | signer の JavaScript、Kotlin、Swift ライブラリの出力がバイト単位で一致することを検査しています。CI では JavaScript と Kotlin を検査し、Swift は 6.3 が必要なため macOS で検査します |
| **パッケージマネージャを使わない** | npm、Gradle、pip は使いません。Python は標準ライブラリだけを使うビルド・検査用のスクリプトにのみ使います。他の処理では C、JavaScript、Kotlin、Swift とハッシュ固定したツールを使います |

## 何を検査しているか

| | |
|---|---|
| 解析器 | Bitcoin Core の `rpc_psbt.json` を含む PSBT ベクタ529件、Blockchain Commons の参照値に対する UR 検査1,174件、継続ファジング、export 集合の固定を検査しています |
| 署名器 | 3つのホストライブラリから同じ項目を検査しています。署名はネイティブ実装の出力とバイト単位で一致する必要があります |
| 両方 | `make check-wasm` で出力形式を検査します。`make check-layout` では、2つの仕様書と3つのホストライブラリに記載した構造体オフセットが C の値と一致することを確認します |

署名は決定論的です。ECDSA は Bitcoin Core と同じく low-R grinding を行い、Schnorr は
`aux_rand` に 0 を渡します。そのため「同じ署名」とは、有効な別の署名ではなく **同一のバイト列** を指します。
ブラウザでもハードウェア署名器の出力を正確に再現できます。
**この方式はマルチシグ対応の前に見直す必要があります。**
[BIP340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki) は、
マルチシグでは決定論的 nonce が危険だと説明しています。
